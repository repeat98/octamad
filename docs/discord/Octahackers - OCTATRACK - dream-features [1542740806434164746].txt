So a huge thing that bugs me about octatrack in context of elektron ecosystem / pattern change management, is that it contains 256 patterns where as all the other devices are 128 patterns.

What this means is if you have multiple devices chained at the hip for patterns to match up (for example a digitakt and an octatrack). This system can only work for the first half of the octatrack patterns, the latter half dont work when using the elektron standard program change system.

What would be cool is a setting somewhere that you can select either banks 1-8 to respond or send to program change or banks 9-16. (So two groups of program change 0-127 switchable).

This would allow 1 octatrack project to be syncable / shared with 2 projects in most of  other elektron devices.

[07.09.2026 08:43] bamshanks
Alright @Bryan T (ukulele owner) got a present for you.

Will need you to test on your end but after I got a local emu up I think we may have sorted your sample clicks:

The 128 / RLEN 4 click: root cause and a patch, on main at 4405a12

We found it and there's a fix. Read docs/RTOS_FORK.md §10.16.4 and §10.16.5 for the mechanism, then §10.17 for the patch.

Mechanism. The sequencer keeps exact fractional event times and fires each recorder trig at ⌊event⌋. The recorder length is computed once per pass and never moves. At 128 / RLEN 4 the period is 20,671.875, so the eighth-of-a-sample accumulates and, once every 8 passes, two arms are 20,671 apart while the recording is 20,672 long. That one-sample overlap at the loop point is the click, once every 2 bars. Measured over ten passes in §10.16.5.

Two corrections to the sheet. The residue doesn't walk in the trig positions; it accumulates in the exact event times and ⌊·⌋ releases it as one whole sample every 1/ε passes. And the length converter multiplies by the truncated reciprocal ⌊2³¹/tempo24⌋, so an exact x.5 quotient rounds down. Your 128 / RLEN 16 row is 82,687 in the firmware, not 82,688 (§10.16.4).

The patch. modules/recorder-seam/ — a ColdFire cave at the length converter's tail (0x40006e0c). It re-derives the length every frame from the sequencer's next step event with the frame builder's own arithmetic and substitutes it only when within one sample of the stock length, so anything that isn't a looping re-trig keeps its RLEN. seam_cave.s is the source, manifest.py pins the bytes, README.md has the register map. Build it with the seamtest remix (remixes/seamtest.py = bus + the cave): REMIX=seamtest make bus, or REMIX=seamtest BUILD=<nn> make image for a card image.

A relatively simple adjustment, but one that I think would improve the usability of the Octatrack.

[18.09.2026 14:55] pinkpanther606_77482
Hello fellow Octatrack users. I have got my head around rewriting parts of the firmware for myself since approx. 1 year but did not really ever start it. I find it really exciting and awesome that so many people are into upgrading the mighty Octatrack and bring the device into a new chapter. What a time to have people revive the OT OS with so awesome features many people thought about and wished for them to exist.

So my take on some features which are not mentioned yet, as of my now-state after reading through the full octa-bam repo. Maybe you are also interested in those and there are people already working and thinking actively about those as well so I want to mention them here. If it belongs somewhere different feel free to tell me.

**Live Pattern Fork / Copy to Empty Slot While Playing**
I’ve always missed a way to duplicate the currently playing Pattern into another slot without selecting/queuing that destination Pattern. The idea would be: keep A01 playing, clone it to A02, edit A02 as a variation, then switch between A01/A02 when ready. Stock OT can copy/paste Patterns, but selecting the destination is tied to normal Pattern selection, so there isn’t really a clean “background fork” workflow.

**MIDI P-lock Slides / CC Glide**
The MIDI LFO Designer already allows excellent continuous CC modulation, including interpolation between its 16 waveform points. What I'd love in addition is Elektron-style glide directly between MIDI CC parameter locks: e.g. CC74=20 on step 1 and CC74=100 on step 9, with a slide flag causing continuous CC interpolation between those actual p-locks. Unlike using the three MIDI LFOs, this could potentially work independently on multiple CC lanes and would automatically follow the distance/timing between p-locks.


[18.09.2026 14:56] pinkpanther606_77482
*
If MIDI CC p-lock slides are feasible, it would also be great to have different interpolation shapes rather than only linear ramps — e.g. Linear, Exponential, Logarithmic and S-curve, perhaps with one Curve/Tension parameter.
The existing LFO Designer UI already feels like a good visual model for this: show the start/end CC values and the resulting curve between them.

**Step-Locked MIDI Program Change**
Allow Program Change to be p-locked like a CC, so one MIDI track could call different synth patches on individual steps rather than Program being tied to the Part/Kit state. This is already possible externally by p-locking an unused CC and converting CC value → Program Change with something like Midihub, so it’s not impossible conceptually — native support would just make it much cleaner. Probably worth warning that some synths cannot load patches fast enough for rapid changes. 

**Pre-Send Filter for the new AUX Bus** (Addition to an existing feature that is being worked on)
A configurable HPF before the shared BusDelay/BusVerb would be very useful to stop kicks/sub-bass muddying the effects. Something like OFF / 60 / 90 / 120 / 160 / 220 Hz, potentially with an LPF too. BusVerb already has internal tone/damping filtering, but that happens inside the reverb architecture rather than filtering the summed signal before it enters the delay/reverb bus, so this would still be a separate useful feature. Maybe I am mistaken here as this is some pretty obvious thing to do on a Aux Bus.

In Austria we like to say, this is my mustard to the topic here.
